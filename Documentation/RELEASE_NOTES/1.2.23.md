## Known bugs to fix

### Broken-pipe writes a crash report — FIXED

Piping inkhaven's stdout into a truncating consumer (`… | head`) made a
`println!` fail with `Broken pipe (os error 32)`, the panic hook fired, and
a `inkhaven-crash-<UTC>.hjson` was written to cwd (seen twice during the
1.2.22 smoke tests).  A SIGPIPE / broken-pipe on stdout is normal shell
behaviour, not a crash.

Fixed in the panic hook (zero-dep — no SIGPIPE reset, so the TUI's internal
/ subprocess pipe handling is untouched): a new **Step 0** detects the
print-macro broken-pipe panic (`crash::is_broken_pipe_panic` — narrow:
requires the `failed printing to std…` prefix *and* a broken-pipe error, so
other output failures like disk-full still report), restores the terminal,
and exits cleanly (0) before the crash-report / rescue steps run.  Verified:
`inkhaven … --dry-run | head` now exits 0 with no crash file; the un-piped
path is unchanged.

## Implementation log

### Broken-pipe crash-report fix (landed)

`crash::install_panic_hook` gains a **Step 0** before the existing
restore/snapshot/rescue/report steps: extract the panic payload string and,
if `is_broken_pipe_panic(msg)`, restore the terminal and `process::exit(0)`.
`is_broken_pipe_panic` is deliberately narrow — `msg.contains("failed
printing to std") && (Broken pipe | os error 32)` — so a disk-full or other
output failure still surfaces a crash report, and a "Broken pipe" string
from anywhere that isn't a print macro is not mistaken for a pipe close.
No SIGPIPE reset (which would risk killing the long-running TUI on any
internal/subprocess pipe close), so zero behaviour change for the editor.
1 unit test (narrow detection: stdout/stderr broken-pipe true; disk-full,
logic panic, non-print "Broken pipe" false).  Live-verified: `… | head`
exits 0, no `inkhaven-crash-*.hjson`.  Suite 1186 → 1187.

### Panic-surface re-audit (landed)

Four parallel auditors swept the whole tree (new Facts/replace/crash,
core store/IO, the TUI layer, export/analysis/import).  The tree is
broadly clean to the 1.2.15 bar — no reachable `panic!`/`unreachable!`,
no `lock().unwrap()` poison surfaces (the codebase uses `parking_lot` +
`.ok()` guards), zero production `.unwrap()`/`.expect()` on user-data
paths outside tests.  The audit converged on one recurring real bug
class — **UTF-8 byte-boundary slicing using an offset taken from a
lowercased / transformed copy** — and a write-durability item.  Fixed:

* **HIGH — `config::parse_color` UTF-8 slice panic.**  A multibyte char
  in a 3- or 6-byte hex string (e.g. theme value `"#aé"` → `len()==3`)
  made `hex[0..1]` split a char and panic — reachable from any HJSON
  theme field, defeating the module's own "never panic on a malformed
  theme" guarantee.  Fixed with an `is_ascii()` gate before the
  byte-slicing.  Regression test added.
* **MED — `app::jump_cursor_to_text` UTF-8 slice panic.**  `byte_col`
  from `line.to_lowercase()` was used to slice the original `line`;
  length-changing folds (Turkish İ, ẞ, ligatures) in non-English prose
  before the match would split a char.  Reachable via fact-check finding
  navigation (`Ctrl+B Shift+J`).  Fixed by slicing the lowercased string.
* **MED — `doctor_scan` naming-scan UTF-8 slice panic.**  Same class:
  a `prose_lc` (lowercased) byte offset sliced the original `prose`.
  Reachable via `inkhaven doctor` on multilingual prose.  Fixed with an
  `is_char_boundary` guard that skips the rare mismatch.
* **MED — non-atomic writes in `store/mod.rs`.**  Four `std::fs::write`
  sites (paragraph + script templates, seeded body, image bytes) routed
  through `io_atomic::write` for torn-write safety, matching the house
  standard (the image-bytes write is the one where a torn write could
  leave a corrupt file).

Suite 1186 → 1188 (two stability regression tests).  Reported but **not**
fixed (low-priority / your call — see notes below).

### Stability items reported (proposed fixes, deferred)

* **`backup::restore` per-entry non-atomic write** (`backup.rs:207`) —
  restores into a fresh dir guarded by an `inkhaven.hjson`-exists check,
  so it isn't overwriting live data; a crash mid-restore leaves a partial
  tree.  Propose: temp-file + rename per entry if hardened.  LOW–MED.
* **`BackupState::save` / `Config::save` non-atomic** (`backup.rs:42`,
  `config.rs:2932`) — a self-healing sentinel and a `#[allow(dead_code)]`
  path; route through `io_atomic` if they go live.  LOW.
* **`storage/engine.rs` string-interpolated JSON SQL** — the JSON store
  builds SQL via `format!` + `sql_escape` (doubles `'`) while the blob
  store uses parameterized `execute_with`.  Not an injection vector today
  (DuckDB standard literals don't process backslashes; the only
  interpolated value is serde-serialized JSON), but fragile — a future
  DuckDB setting or new interpolated field could break it.  Propose:
  migrate the JSON methods to parameterized queries.  LOW (fragility).
* **`gen_fixture.rs:274` `% pool.len()`** — panics on an empty pool, but
  only called with non-empty constant word pools in the dev-only
  `gen-fixture`.  LOW (dev tool).
* **`facts extract` EOF prompt** — flagged as a possible busy-loop, but on
  inspection the `""` arm already treats EOF as "no" and the loop
  terminates; **not a bug**, no change.

### storage/engine.rs SQL hardening (landed)

Migrated the JSON + blob stores off string-interpolated SQL onto bound
parameters, removing the `sql_escape`/`format!` pattern entirely from
`engine.rs`:

* New `StorageEngine::select_all_with(sql, args)` — the parameterized
  counterpart to `select_all` (binds via `params_from_iter`), so SELECTs
  that filter on an id no longer interpolate.
* `add_json_with_id` / `update_json` → `execute_with` with placeholders;
  the JSON document binds as a parameter and casts in-SQL via
  `CAST(? AS JSON)` (no `'…'::JSON` string literal).
* `get_json` / `get_blob` → `select_all_with`; `drop_json` / `drop_blob`
  → `execute_with`.  `list_all` had no interpolation (unchanged).
* `engine::sql_escape` is now unused and removed.

Not an injection vector before (the only interpolated value was
serde-serialized JSON, and DuckDB standard literals don't process
backslashes), but the binding approach is robust by construction and
removes the fragility (a future DuckDB `backslash_escapes` setting or a
new interpolated field could have broken quote-doubling).  New adversarial
round-trip test: a JSON doc with single/double quotes, backslashes, and a
`'; DROP TABLE …` string round-trips intact and leaves the table whole.
Suite 1188 → 1189.

Related (out of this scope, flagged): `progress/store.rs` has its **own**
`sql_escape` and still interpolates `book` strings into SQL — same
fragility class, worth the same treatment in a follow-up.

### progress/store.rs SQL hardening (landed)

The follow-up flagged in the engine.rs hardening.  `progress/store.rs`
had its **own** `sql_escape` and interpolated `book` (and integer)
values into five SELECTs via `format!`.  All five now use the shared
`StorageEngine::select_all_with` with bound parameters (`baseline_for`,
`last_n_daily`, `status_promotions_recent`, `writing_days_recent`,
`active_seconds_in_range`); the local `sql_escape` is removed.  The
INSERTs already used `execute_with`.  No interpolated SQL remains in the
progress store.  11 progress tests green (they round-trip baselines +
events through the parameterized paths).

### R.3 polish — in-modal opts toggles (landed)

The deferred 1.2.22 R.3 item.  The project-replace review modal now
carries its `ReplaceOpts` and lets you change the matching mode without
leaving the review: **`w`** toggles whole-word, **`i`** ignore-case,
**`x`** regex — each re-runs the scan (`retoggle_replace_review` flips a
copy of the opts and re-enters `open_replace_review`).  The header shows
the active mode (`[whole-word]` / `[substring]` / `[regex]` /
`…, ignore-case`) via the new `replace::opts_label`; the footer lists the
toggle keys.  So the editor now reaches the same regex / substring /
case modes the CLI's `inkhaven replace` flags do, starting from the safe
whole-word default.

Engine validated end-to-end via a CLI opts smoke (substring catches a
prefix inside a word; ignore-case matches a lowercased query while
case-sensitive finds nothing; regex matches) — the toggles drive exactly
these `scan_project` paths.  1 unit test (`opts_label`).  Suite 1189 →
1190.
